Goal 契约 & 实机诊断 架构

Open-AutoGLM 的目标子系统如何把一句自然语言任务，编译成一份可验证、隐私安全、跨轮持久的声明式契约， 并在 Plan-Execute-Reflect 循环里用它做 finish 门控——这是长任务不"提前假完成"、不"带错目标空转"的核心。 本文档同时覆盖配套的实机诊断技能如何把 trace 信号归因回源码。

1 · 总览

一次任务 = 一份 GoalContract。它在图起点编译一次，之后跨所有 replan 轮次复用， finish 时被逐条对账。目标不再是"屏幕上出现某个关键词"，而是"一组带类型化验证方式的成功标准"。

声明式契约

GoalContract 由 CriterionSpec[]（成功标准）、约束、非目标、验证策略组成。每条标准声明自己用哪种 verification 验证。

独立需求交叉校验

TaskRequirementSet 从原始任务独立抽取需求，ContractAdequacyValidator 校验契约是否真的覆盖需求——契约不能自证充分。

类型化证据

证据是 ObservedFact（中性、无极性），由 Matcher 判定匹配，按来源分权威等级（device > accessibility > …）。

Fail-closed finish 门

execute 只声明 pending_finish；reflect 用 evaluator 验证证据才置 finished=True。unknown/缺失 → replan，永不自动升级为成功。

隐私分层

完整契约 + 截图留在进程内 RuntimeGoalContext/RuntimeObservationContext，绝不进 state/trace/checkpoint。

可信恢复

checkpoint/goal_resume.py 用 HMAC 绑定；evidence ledger 在 checkpoint 出口清空，进度只从可信投影重水合。

一句话对比：旧设计 = "看屏幕上有没有 播放/详情/评论 这些词就算完成"； 新设计 = "编译一份可验证契约 → 每步收集类型化证据 → finish 时逐条对账、程序信号优先、不满足就继续"。

4 · 编译链：一句话 → 一份契约

compile_goal_contract() 按 External > LLM > Heuristic 顺序尝试（graph/goal_compiler.py）。

ExternalGoalCompiler

benchmark / eval 注入的预制契约，标记 compile_status=user_override。必须附带独立的 requirement set 做绑定校验。

LLMGoalCompiler

一次 structured-output 调用（失败重试一次）。产出 verification_strategy=hybrid。对实体任务会合成一条 required vlm_judge 标准。

HeuristicGoalCompiler

永不失败的兜底。抽取 app/ordinal/entity，产出 vlm_judge_at_finish 弱契约。不驱动自动成功——evaluator 仍要求点名 + grounded 证据。

5 · Validator：让 Goal 能力"真正有牙齿"

Goal 能力的关键不在编译，而在两道独立校验：编译前的 adequacy 校验（契约是否覆盖需求）、finish 时的 evaluator 校验（证据是否满足标准）。

5.1 ContractAdequacyValidator — 契约不能自证充分

TaskRequirementExtractor 从原始任务独立抽取需求（operation_kind、target_app、ordinal、entity hashes、terminal_state、constraints），再由 ContractAdequacyValidator 逐项比对契约是否覆盖：

# graph/goal_requirements.py（简化）
if requirements.target_app_identity != contract.target_app_hint:   reasons.append("target_app_uncovered")
if requirements.ordinal != contract.ordinal:                       reasons.append("ordinal_uncovered")
if entity_hashes 不相交:                                          reasons.append("target_entities_uncovered")
if 无 semantic predicate 且 无 required vlm_judge:            reasons.append("semantic_criterion_missing")
if not terminal_state_covered(...):                             reasons.append("terminal_state_uncovered")
关键修复 db3fa31：需求侧与编译侧原来各写一套分词器（compiler 剥掉"视频"、extractor 保留），实体哈希永不相交，几乎所有搜索/选择任务被判 target_entities_uncovered 终止。抽出单一来源 extract_entity_spans 两边共用后修复。
放宽策略：required vlm_judge 现在算作语义/终态兜底覆盖；operation_unknown 不再算 ambiguity（未知动词降级到 LLM + vlm_judge，只降低 confidence），不再一开始就终止任务。

5.2 finish 时的 evaluator — 逐条对账

AggregatingGoalEvaluator 逐条 _check_criterion，再做第二遍"程序信号推翻 vlm_judge 自称"。全 typed 契约还会再跑纯函数 PureGoalEvaluator。

核心不变量
  • criterion 未在 matched_terminal_evidence 点名 → missing（硬门）
  • required 缺失 → failure；全 required 命中 → success；其余 → unknown（不升级为成功）
  • 程序信号矛盾（accessibility/app-activity）压过 vlm_judge 自称
  • placeholder screen_reference（region-1/screen/区域2）→ 拒绝，视为无判别信息
HEAD 关键修复（finish 门回归）：编译器给 vlm_judge 标准绑了 semantic.entity_matches，其期望值是实体哈希， 但 finish 时 provider/VLM 产出的是屏幕原文，casefold_exact(hash, 原文) 永远 contradicted。 修复：_is_hash_bound_expectation 识别哈希期望，把这种矛盾判为"域不匹配"而非反证，回退到 _check_vlm_judge（有 grounded reference 即可）。

7 · 隐私边界与证据权威

完整契约值、截图、原始语义值绝不跨越运行时边界进入 state/trace/checkpoint。

运行时隔离
  • RuntimeGoalContext：完整契约 + requirement，__getstate__ 抛异常禁止序列化
  • RuntimeObservationContext：节点内截图上下文，用后 invalidate()
  • state 只存 runtime_reference + 脱敏投影（to_state_payload）
predicate 投影策略
  • PUBLIC_CHECKPOINT：app 身份等公开值可全量落盘
  • PRIVATE_RUNTIME：ui.text_equals/semantic.entity_matches 等 → state/trace 仅 metadata，checkpoint omit
  • runtime-only predicate 必须从 checkpoint 省略（__post_init__ 强制）

证据权威分级（fact_providers.py）

同一 predicate 有多来源事实时，高权威源压过低权威源，减少长任务里的证据噪声误判：

device / external_probe · tier 5
accessibility · tier 4
screen_object · tier 3
mark / visual_region · tier 2
whole_screen · tier 1

8 · 为什么这提升了长任务能力

长任务能力不来自单点，而来自几个机制的组合。

机制对长任务的作用
契约编译一次、跨轮复用目标不随 message 压缩丢失——几十步后 Goal 仍在；replan 时 goal_node no-op 不重编译
adequacy 交叉校验编译出的契约必须覆盖独立抽取的需求，否则一开始就 fail-closed，不让 agent 带错目标空跑几十步
finish 是声明不是成功防止长任务"提前假完成"的核心闸门：证据不够就继续，而不是乐观结束
程序信号 > vlm_judge 自称模型说"做完了"但 accessibility/app-activity 反证 → 推翻，防止长任务里模型自欺
证据账本 + 权威分级reflect 维护 bounded ledger，PureGoalEvaluator 做纯函数折叠；高权威源压过低权威源，减少噪声误判
净效果：agent 在长任务里不会因一次乐观判断提前结束，也不会带着无法满足的目标空转——这正是"长任务能力"的来源。

10 · 已知风险与边界

诚实记录当前尚未闭合的点，供后续修复决策。

after_goal takeover 路由不可达

after_goal 的终止守卫 if finished/error: return "end" 先执行，而 goal_node 失败时同时返回 finished=True 和 retry_policy=takeover，因此新加的 takeover 分支目前永不触发（单测用 finished=False 通过，但生产不可达）。

vlm_judge 语义强度受限

hash-bound 回退到 _check_vlm_judge 后只校验"存在非占位 screen_reference"，不校验观测实体是否等于目标实体——错误实体自证仍可能通过。这是 vlm_judge 固有信任级别，非本轮新增。真正的语义精确匹配依赖 visual/whole_screen_fact_extractor 实际接入（默认 None，无默认实现）。

needs_recompile 无 writer

mid-task 契约切换目前只能通过 configurable["task_goal_contract_override"]；运行时没有写 needs_recompile 的路径。

checkpointer 未接线

graph.compile() 无 checkpointer，可信 resume 逻辑存在但运行时不触发（"runtime saver not enabled"）。
