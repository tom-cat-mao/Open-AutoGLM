# Future Plan：任务级规划层（task_plan）

> 状态：**待讨论，不在本轮实施**。来源：20260803 讨论（用户提出"是否该加一个规划节点"）。
> 结论：要规划层，但**不加新节点**——goal_node 从"编译契约"扩展为"编译契约+分解阶段"。

## 问题定义
当前架构各层分工有空洞：契约说 WHAT（完成长什么样）、agenda 说 STATUS（哪些已满足）、
**没有 PATH（按什么顺序走、现在走到哪）**。真机证据：
- 0731 博主页内输错关键词（阶段错位：模型不知自己在"页内找银石"阶段）
- 0731 内容已打开不 finish（没有"还剩什么"的清单）
- 日历振荡（无阶段策略）

## 设计（讨论稿）
1. **编译时生成**：goal_node 编译契约的同一次/紧随调用顺带产出 `state["task_plan"]`：
   3-6 个阶段，每阶段三件套 = 页面级目标 + 可观察完成信号 + 兜底策略。
   禁止控件/坐标级描述（一屏就碎）。完成信号挂现有词汇（agenda 标准/activity/可见文本）。
2. **输入**：任务原文 + GoalContract + step0 截图 + app_registry 摘要 +（可选）大 App 宏流程一句话先验。
3. **注入**：context block 加 `task_plan` section，当前阶段高亮（tracker：progress_note 自报 +
   agenda 状态推导）。标注"参考路径，以截图为准"——信念非授权，与契约同原则。
4. **修订**：走现有 replan→goal 路由重编（stuck/验收拒绝/阶段 K 次未推进触发）。
5. **协同复利**：阶段转换 = 天然的有类型里程碑，喂给 window-budget 的
   `continuation_credential`（解决纯 vlm_judge 契约凭据饿死问题）；预算 pacing 有参照系
   （"阶段3/5 用了 80% 预算"）。
6. **成本**：任务级 1 次调用 + 罕见重编；与单调用/步方向不冲突。

## 必须防的坑
1. 计划僵化毒化：计划是可修订信念，模型有权偏离，截图优先；错的计划硬注入比没有更糟。
2. 与 goal contract 重复建设：独立价值只在顺序+当前位置+阶段策略，评审时用这条卡重复。

## 待讨论的开放点

- 重编触发条件的阈值
- 数据结构定稿（stage/done_signal/fallback/tracker）
